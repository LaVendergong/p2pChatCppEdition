# 00 需求与目标

## 1. 产品定位

终端里的多人聊天工具。用户在任意 SSH 会话中启动 `chatt`，即可登录服务端、加入房间、
收发文本消息、翻阅历史。服务端 `chatd` 单机部署，负责连接管理、消息路由与持久化。

不做的事情（明确排除，避免范围蔓延）：

- 不做图形界面、不做 Web、不做移动端。
- C/S 模式不做端到端加密（服务端要存历史并广播，语义上是"信任服务器"；仅传输层可选 TLS）。
  **P2P 模式例外且已实现**：消息不经服务器，见 `11-P2P架构.md` §5.6。
- 不做文件/图片传输（M0–M5 只支持 UTF-8 文本；协议预留 `MSG_SEND` 的 kind 字段）。
- 不做分布式集群（单机多核；协议与存储预留扩展位，但不实现）。

## 3. 非功能需求

| 编号 | 需求 | 指标 |
| --- | --- | --- |
| N1 | 消息容量 | 单房间 1000 万条以上，单机 1 亿条可用 |
| N2 | 写入吞吐 | 单机 ≥ 5 万条/秒（小消息，批量 fsync 策略） |
| N3 | 写入延迟 | p99 ≤ 10 ms（同机回环） |
| N4 | 历史查询 | 按 ID 定位任意消息 O(log S)，S 为分段数；单页返回 ≤ 5 ms |
| N5 | 并发连接 | 单机 ≥ 5000 长连接（epoll 单线程 IO + 工作线程池） |
| N6 | 稳定性 | 连续运行 7×24h 无内存增长（Valgrind/ASan 无泄漏） |
| N7 | 崩溃一致性 | 断电后重启，已 ACK 消息 100% 可恢复；半截记录丢弃 |
| N8 | 内存占用 | 服务端常驻 ≤ 200 MB（1000 万消息规模），索引按需加载 |
| N9 | 依赖 | 仅 glibc / pthread / C++20 标准库，不引入第三方库 |
| N10 | 可观测性 | 结构化日志、`--stats` 运行时统计、SIGUSR1 打印统计 |

## 4. 关键设计取舍（面试级说明）

1. **为什么自定义二进制协议而不是 JSON/文本行？**
   文本协议解析需要分配、转义、边界处理，且长度不可预知易被恶意构造拖垮。
   二进制帧有固定头 + 显式长度，解析 O(1) 且可做上限校验，适合高吞吐与"精确"要求。

2. **为什么 append-only 分段日志而不是 SQLite？**
   题目约束"只有系统底层依赖"。append-only 顺序写是磁盘最快路径，天然支持崩溃恢复
   （尾部截断即可）；分段让历史查询无需全量索引，也便于归档删除。

3. **为什么单线程 epoll + 线程池而不是 one-thread-per-connection？**
   5000 连接时线程栈（默认 8MB）就是 40GB 虚拟内存，且上下文切换开销大。
   epoll 单线程处理 IO 事件，重活（fsync、序列化）丢给线程池。

4. **一致性模型**：单房间内消息 ID 由存储引擎串行分配，保证全序；ACK 在 fdatasync
   之后发出，因此"客户端看到的顺序" = "磁盘上的顺序"。不追求跨房间事务。

## 5. 验收标准（Definition of Done）

- M0：两端能编译，客户端连上服务端，一条消息能经服务端广播回自己。
- M3：两个客户端互相收发中文消息；重启服务端后历史仍在；`kill -9` 后不丢已 ACK 消息。
- M5：压测脚本灌入 1000 万条消息，随机读 10 万次，p99 延迟达标；ASan 无报错。
- M6：7×24 小时浸泡测试 72h 内存曲线平稳。
