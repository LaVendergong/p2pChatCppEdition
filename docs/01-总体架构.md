# 01 总体架构

## 1. 进程与部署形态

两个可执行文件，不依赖守护进程或注册中心：

```
chatd  服务端：监听 TCP，管理连接、房间、消息持久化
chatt  客户端：终端 UI，单进程，一个 TCP 连接
cht-load / cht-ctl  辅助工具：压测灌数据、离线查看存储文件
```

单机部署即可。服务端数据目录结构：

```
data/
├── meta.db                # 服务端元信息：账号表、房间表
└── rooms/
    ├── public/            # 房间名即目录名（已做路径安全校验）
    │   ├── 000000000000000001.seg
    │   ├── 000000000000000002.seg
    │   └── room.meta      # last_msg_id / 记录数 / 分段表
    └── alice__bob/        # 私聊房间
```

## 2. 分层

```
        ┌─────────────────────────────────────────────┐
 chatt  │ ui(渲染)  editor(输入编辑)  commands(斜杠)  │
        │            client_app(状态机/重连)          │
        ├─────────────────────────────────────────────┤
         │           net(连接/收发缓冲)  │ codec(帧)  │
        ╞══════════════════════════════════════════════╡  ← 公共库 chat_common
 chatd  │  server(epoll 循环)  session  router         │
        │  storage(分段日志/索引)  auth  config         │
        ├─────────────────────────────────────────────┤
        │ log  time  buffer  crc32  sha256  fs  socket  │
        └─────────────────────────────────────────────┘
                         POSIX / libc / C++20
```

公共库 `chat_common` 只放"两边都会用"的东西，不放业务逻辑。业务逻辑各自留在
`server/`、`client/` 内，**不做多余抽象**（用户规则：一个功能一个函数能写完就不拆十个）。

## 3. 线程模型

### 服务端 chatd

```
主线程 (main)
 └─ epoll 事件循环 (io loop)          ← 唯一读写 socket 的线程
     ├─ 解析帧 → 生成 Task 丢到队列
     └─ 消费完成队列 → 写回响应

工作线程池 (N = CPU 核数，可配置 2~8)
 ├─ 执行：存储写入(fdatasync)、历史查询、密码哈希、消息扇出
 └─ 结果通过 mutex + 队列交回 io loop
```

原则：

- **socket 只由 io 线程碰**，避免加锁；工作线程只产出字节缓冲，由 io 线程写。
- **发送是"攒一轮再写"**：广播只入队，本轮事件处理完统一 `writev`。这是实测最大的一处优化
  （QPS 4000 → 11 万，p99 171 ms → 11 ms），因为原来的"每条消息逐个会话 send"在高频写入下
  会产生大量 syscall。
- 存储引擎内部自带 mutex（每房间一把）；`append` 由 io 线程调用（写 page cache，微秒级），
  `fdatasync` 与提交回调由 flusher 线程批量完成。
- 定时任务（超时踢连接、统计、心跳）挂在 epoll 循环里，不用单独线程。

### 客户端 chatt

客户端是**单线程 + poll**：同时监听 stdin 与 socket，任一可读就处理。
没有并发需求，单线程最简单也最稳（不会出现 UI 撕裂竞态）。

```
poll([stdin, sockfd, signalfd]) → 事件分发 → 渲染(diff 输出到 stdout)
```

## 4. 关键数据流

### 发送一条消息

```
用户键入 → editor 缓冲 → Enter
  → client 组帧 MSG_SEND(room, text, client_msg_id=本地自增)
  → TCP → chatd io loop 收到 → 校验(长度/权限/房间)
  → 投递工作线程 → storage.append()  [写 seg 文件 + 索引 + fdatasync]
  → 返回 msg_id → 组装 MSG_RECV 广播帧（一帧一份缓冲，8 个会话共享）
  → io 线程把帧放进每个 session 的待发队列，不立即写
  → 本轮 epoll 事件处理完，统一 writev 发出（一次系统调用写多段，多条消息合并）
  → 客户端收到 MSG_RECV：按 msg_id 去重、插入有序列表、渲染
  → 客户端收到 MSG_SEND_ACK：标记本地消息为已确认（失败则标红重发）
```

### 拉历史

```
客户端 PgUp 到顶 → HISTORY_REQ(room, before_id=最早本地id, limit=50)
  → storage.read_before(room, id, limit)：分段二分 + 反向顺序读
  → HISTORY_ACK(room, [MSG_RECV ...])  按 id 升序返回
  → 客户端前插，保持窗口大小
```

## 5. 内存与大数据策略

| 场景 | 策略 |
| --- | --- |
| 单房间千万消息索引 | 磁盘上按 id 排序的 `idx` 文件（16B/条：id + offset），内存只缓存分段头，查询用 `pread` 二分 |
| 客户端历史 | 内存保留最近 2000 条，超出丢尾部；上翻按需从服务端拉 |
| 消息体 | `std::string` + 短字符串优化（≤15 字节零分配）；房间内广播共享 `shared_ptr<const Message>`，不逐客户端拷贝 |
| 连接缓冲 | 每连接固定读缓冲 16 KB + 动态扩容上限 1 MB，防 DoS |

## 6. 技术选型与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 语言标准 | C++20 | 需要 `std::span`/`std::string_view`/`jthread` 可用但不强依赖 |
| 构建 | CMake ≥ 3.20 | 系统包即可装，跨 WSL/原生 Linux 一致 |
| IO 模型 | epoll **LT** + 非阻塞 | LT 不需要"必须读到 EAGAIN"的纪律，写事件管理也更简单；千级连接下开销可忽略。不引入 libuv |
| 序列化 | 手写 TLV（见 03） | 零依赖、可跳过未知字段、易于 fuzz |
| 持久化 | append-only seg + fdatasync | 顺序写最快，恢复简单 |
| 并发 | pthread（`std::thread`）+ mutex | 够用，避免自造 lock-free |
| 测试 | 自研极简 assert 框架 | 不引入 gtest |
| 日志 | 自研异步日志 | 不引入 spdlog |
