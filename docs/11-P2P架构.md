# 11 P2P 架构（chatsig + 直连 + 打洞 + 中继）

目标：**任意两台联网电脑，输入对方用户名即可建立会话**。局域网零配置，跨网自动打洞，
打洞失败自动中继。消息各自存本地。

## 1. 为什么必须有信令服务器

纯 P2P 的物理限制：

- 家用/公司电脑大多在 NAT 后面，不知道自己对外是什么地址；
- 即使知道，NAT 也会丢弃"没有先发出去"的入站包；
- 所以通信前必须先**交换双方的公网映射地址**——这件事只能由双方都能访问的第三方完成。

因此拓扑是"信令 + 尽力直连"：

```
   A ──── TCP(信令) ────►  chatsig  ◄──── TCP(信令) ──── B
   │                        (VPS)                        │
   └────────── 媒体通道：直连 > 打洞 > 中继 ──────────────┘
```

信令只传"地址"和"控制消息"，**不传聊天内容**（中继模式除外，且中继是端到端转发）。

## 2. 组件

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| `chatsig` | VPS（有公网 IP） | 端点注册、地址查询、在线状态、中继转发 |
| `chatt --p2p` | 每台电脑 | 同时**监听**（被连）和**发起**（连人）；消息存本地 |

## 3. 连接建立流程

```
1) 客户端启动
   chatt --p2p --user alice --listen 7800 --sig sig.example.com:7900
   → 连 chatsig，LOGIN（用户名+密码，沿用现有 salt+sha256）
   → PEER_REGISTER { tcp_port=7800 }
   ← PEER_REGISTER_ACK { public_ip, public_port }   （chatsig 看到的对端地址）

2) 发起会话：用户输入 /chat bob
   → PEER_LOOKUP { bob }
   ← PEER_LOOKUP_ACK { candidates: [
        {kind=lan,   ip=192.168.1.7, port=7800},
        {kind=public,ip=1.2.3.4,     port=41235} ] }
   （chatsig 同时给 bob 推 PEER_INCOMING，让它开始等待）

3) 按优先级尝试建立媒体通道
   a. LAN 候选直连      TCP connect 超时 800 ms
   b. 公网候选直连      TCP connect 超时 800 ms（多数 NAT 会失败）
   c. 中继              RELAY_OPEN 申请，双方配对后由 chatsig 转发（已实现）
   d. UDP 打洞          阶段 3（可选优化，降低延迟与服务器带宽）

4) 成功后
   在媒体通道上跑 CHTP（复用现有协议），room = 对方用户名
   收到的消息写入本地 data/peers/<peer>/ 分段日志
```

两条连接（信令 + 媒体）是独立的：信令断了不影响已建立的会话，媒体断了会触发重连。

## 4. 协议扩展（CHTP 兼容）

沿用 24 字节帧头 + TLV，只新增类型与 tag。老版本客户端收到未知类型回 `ERROR(UNSUPPORTED)`，不断连。

### 4.1 新增消息类型

| 值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| 0x0060 | `PEER_REGISTER` | C→Sig | 注册端点（tcp_port） |
| 0x0061 | `PEER_REGISTER_ACK` | Sig→C | 返回 public_ip / public_port |
| 0x0062 | `PEER_LOOKUP` | C→Sig | 查询某用户的可连地址 |
| 0x0063 | `PEER_LOOKUP_ACK` | Sig→C | 候选地址列表（含 lan/public） |
| 0x0064 | `PEER_INCOMING` | Sig→C | 有人要连你（带对方候选） |
| 0x0065 | `PEER_OFFLINE` | Sig→C | 对方下线通知 |
| 0x0070 | `RELAY_OPEN` | C→Sig | 请求中继到某用户 |
| 0x0071 | `RELAY_DATA` | 双向 | 中继透传的原始 CHTP 帧 |
| 0x0072 | `RELAY_ACK` | Sig→C | 中继配对成功/失败 |
| 0x0080 | `CRYPTO_KEX` | 双向 | 端到端加密握手：身份公钥 + 本次连接的临时公钥 |

### 4.2 新增 tag

| tag | 名称 | 类型 | 用途 |
| --- | --- | --- | --- |
| 0x0019 | `LAN_IP` | str | 客户端自己上报的局域网地址 |
| 0x001A | `TCP_PORT` | u16 | 监听端口 |
| 0x001B | `CANDIDATES` | array | 候选地址列表 |
| 0x001C | `PEER_NAME` | str | 目标/来源用户名 |
| 0x001D | `PUBLIC_IP` | str | chatsig 观察到的公网地址 |
| 0x001E | `PUBLIC_PORT` | u16 | chatsig 观察到的公网端口 |
| 0x001F | `CAND_KIND` | u8 | 0=lan 1=public 2=relay |
| 0x0021 | `KEX_PUB` | str(32) | X25519 身份公钥（长期，原始字节） |
| 0x0022 | `KEX_EPH` | str(32) | 本次连接的临时 X25519 公钥（前向保密） |
| 0x0023 | `CIPHER` | str | 密文 ‖ 16 字节 Poly1305 标签 |
| 0x0024 | `NONCE` | u64 | 消息序号，同时用作 AEAD nonce（从 1 递增） |

候选元素本身是一组 TLV：`CAND_KIND + LAN_IP + TCP_PORT`。

## 5. 身份与安全

**阶段 1–4 的状态**

- 信令登录沿用 `salt + sha256(salt:password)`，用户名全局唯一，防止顶替。
- 媒体通道明文（阶段 5 已改为端到端加密，见 5.6）。

**仍然存在的风险（明确记录，不掩盖）**

- 中间人可以伪装成信令服务器（无 TLS 时）→ 生产部署应把 chatsig 放在 TLS 后面或用 `stunnel`。
  这条风险决定了下一条：**指纹比对必须通过另一条信道（当面/电话/其他 IM）**，不能通过聊天本身传递。
- 前向保密只到**连接级**（临时密钥每连接一把，用完即弃）：会话内的消息不能单独前向保密，
  即"拿到某条消息的密钥就能解同一连接的其他消息"。按消息级 FS 需要双棘轮，属于后续。

## 5.6 端到端加密（阶段 5，已实现）

媒体通道建立（`HELLO`/`HELLO_ACK`）后，双方立即各发一次 `CRYPTO_KEX`，
里面同时带**长期身份公钥**和**本次连接的一次性临时公钥**：

```
A: CRYPTO_KEX{ kex_pub = A_id(32), kex_eph = A_eph(32) }
B: CRYPTO_KEX{ kex_pub = B_id(32), kex_eph = B_eph(32) }

secret = DH(A_id,B_id) ‖ DH(eph_小, id_大) ‖ DH(id_小, eph_大) ‖ DH(A_eph,B_eph)
salt   = 小id ‖ 大id ‖ 小eph ‖ 大eph          （"小/大"按身份公钥字节序）
okm    = HKDF-SHA256(salt, secret, info="chatt-p2p/v2", 64 字节)
方向   = 身份公钥较小方用 okm[0:32] 发送、okm[32:64] 接收，另一方相反
```

四段 DH 各管一件事：

| 段 | 作用 |
| --- | --- |
| `DH(id,id)` | 身份绑定：没有对方身份私钥就算不出这段 |
| `DH(eph,id)` / `DH(id,eph)` | 把临时密钥"挂"到身份上——临时密钥本身没有身份，靠这两段与身份绑定 |
| `DH(eph,eph)` | 前向保密：两把临时私钥用完即弃，事后只有身份私钥也拼不出完整 secret |

> 注意：这两段的**拼接顺序必须按身份公钥字节序规范**，否则两端算出的 secret 串接顺序不一致
> （A 的"我的临时×对方身份"和 B 的"我的临时×对方身份"是两个不同的 DH 值，不能同位置）。

要点：

- **方向不靠"谁是发起方"**：中继模式下双方都是发起方，只有公钥字节序是双方都能确定的。
- **每次连接都换临时密钥**，所以同两个人反复连接得到的会话密钥都不同（也避免 nonce 重用）；
  派生完成后立刻把临时私钥清零。
- 聊天消息：`MSG_SEND{ nonce = 计数器, ts_ms, cipher = 密文 ‖ tag }`，
  AEAD = ChaCha20-Poly1305，nonce = 计数器（12 字节，前 8 字节小端），
  AAD = `"chatt-p2p/msg-v1"`。`ts_ms` 仍是明文（元数据：时间与长度可见，内容不可见）。
- **接收侧强制**：没握手成功就不发消息（输入行内容还给用户，不会假装发出）；
  收到明文 `MSG_SEND`、序号回退/重放、标签校验失败一律丢弃并提示，绝不显示内容。
- **身份绑定（TOFU）**：首次连接把 `用户名 → 指纹` 记进 `known_peers.txt`；
  之后再遇到同一用户名但指纹不同，屏幕明确告警（可能是冒名），需要 `/trust <name>` 人工确认。
- 指纹 = `SHA-256(公钥)` 前 16 字节，`xxxx:xxxx:...` 8 组，方便人眼核对（`/fingerprint`）。
- 加密只覆盖**聊天内容**；`HELLO`/`PING`/信令帧仍是明文（不含隐私数据）。
- 中继模式下 `CRYPTO_KEX` 和消息都被包在 `RELAY_DATA` 里，**chatsig 只看到密文**。

复用的密码学实现全部手写在 `src/common/crypto.cpp`，正确性由 RFC 7748 / RFC 8439 / RFC 5869
官方向量保证；此外 `scripts/e2e_sec_test.py` 用**纯 Python 独立实现**的同一套算法连真实客户端，
验证派生规则、指纹、重放与篡改拒绝（自己实现的密码学不能只跟自己对齐）。

## 5.5 中继协议（阶段 4，已实现）

当所有直连候选都失败时：

```
A: RELAY_OPEN{peer_name=bob}
S: 记录 waiting[alice]=bob，给 bob 推 PEER_INCOMING{peer_name=alice, relay_flag=1}
B: 收到后自动回 RELAY_OPEN{peer_name=alice}
S: 发现 waiting[alice]==bob 且收到 bob 的申请 → 配对
S: 给双方回 RELAY_ACK{code=0, peer_name=对方}
A/B: 各自建立一个 relay 模式的会话（HELLO 也走中继）
之后  A: RELAY_DATA{payload = 内层完整 CHTP 帧}  →  S 原样转发给 B
```

要点：

- **chatsig 不解包内容**，只按配对关系转发 `payload`，聊天内容对它是不透明的。
- 一条 TCP 连接（信令）同时承载控制消息和中继数据，不需要额外端口。
- 阶段 4 只支持**一条中继会话**（同时跟一个人中继），多条需要 `peer_name` 路由，列为后续。
- 任一方断线时 chatsig 会给对端推 `PEER_OFFLINE`，双方清理会话。

## 6. 本地存储

```
data/
├── peers/
│   └── bob/                 ← 对端用户名即目录名（已做路径安全校验）
│       ├── 000...001.seg    ← 复用现有分段日志
│       └── room.meta
├── identity.key             ← 长期 X25519 私钥（64 个 hex 字符），首次启动自动生成
├── known_peers.txt          ← TOFU：每行 "用户名<TAB>指纹"
└── meta.db                  ← 本地自己的账号（连信令用）
```

> 本地历史是**明文**（这是自己电脑上的日志）。端到端加密保护的是"传输途中"，
> 不解决本机磁盘被读——那属于磁盘加密的范畴。

复用 `RoomStore`，只是 `room` 名字换成对端用户名。**双方各存一份**，天然不依赖服务器。

## 7. 分阶段计划

| 阶段 | 内容 | 覆盖场景 | 状态 |
| --- | --- | --- | --- |
| **1** | chatsig + TCP 直连（LAN 候选优先） | 局域网 100%；一方有公网 IP 也 OK | ✅ 完成 |
| **4** | chatsig 中继兜底 | **剩余全部场景**（含对称 NAT / 企业网） | ✅ 完成 |
| **5** | 身份密钥 + 端到端加密 + TOFU 指纹 | 直连与中继**都**加密，冒名可见 | ✅ 完成（连接级前向保密，四重 DH） |
| **2** | TCP 同时打开（simultaneous open） | 部分跨网（优先级已降低，中继已覆盖） | 未开始 |
| **3** | STUN + UDP 打洞 + 轻量可靠层 | 多数家庭宽带（70–90%，用于降低延迟和服务器带宽） | 未开始 |

> 先做阶段 4 而不是阶段 3 的原因：中继能用约 100 行覆盖"打洞失败"的全部场景，
> 而 UDP 打洞还需要在自研可靠层上做分片/ACK/重传/排序/流控。先保证"一定连得上"，
> 再考虑"尽量不走服务器"。

阶段 1 就能满足"输入用户名就聊"（同网段），也是后面所有阶段的基础。

## 8. 为什么不做 UDP 一步到位

UDP 打洞需要在 UDP 上自己实现可靠传输（分片、ACK、重传、排序、流控），这是独立的一大块，
且没有 TCP 直连作为基线就无法判断"打洞失败"是网络问题还是可靠层 bug。
先用 TCP 打通端到端链路（协议、存储、UI 全部复用），再加 UDP 作为补充路径。

## 9. 失败与降级

| 情况 | 行为 |
| --- | --- |
| 信令连不上 | 提示；已建立的会话不受影响；后台重试 |
| 对方离线 | `PEER_LOOKUP_ACK` 返回空候选 → 提示"对方不在线"（消息不排队，本地仍记录你发出的内容） |
| 所有候选都连不上 | 提示"无法建立直连"；阶段 4 后自动走中继 |
| 媒体通道断开 | 会话标记 `○`，按 1/2/4/8 s 退避重连 |
| 同一用户多设备 | 阶段 1 只保留最后一次注册（后注册覆盖），多设备需要设备 ID，列为后续 |
| 握手未完成 | 状态栏 `e2e:handshake`；此时发消息会被拒绝并把内容退回输入行 |
| 对端公钥是低阶点 / 与自己相同 | 拒绝对话加密（提示密钥交换失败），不降级为明文 |
| 指纹与记录不符 | 屏幕告警并标记 `e2e:KEY-CHANGED`；`/trust <name>` 才覆盖记录 |
| 收到明文/重放/被篡改的消息 | 丢弃并提示，不显示内容 |
