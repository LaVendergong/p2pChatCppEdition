# 04 存储引擎设计

目标：千万级消息、顺序写、崩溃可恢复、按 ID 随机定位。全部基于 POSIX 文件 API 手写。

## 1. 目录布局

```
data/
├── meta.db                          # 账号表（每行一条 TLV 记录）
└── rooms/<room>/
    ├── room.meta                    # 分段表 + 最后消息 id（原子替换写）
    ├── 000000000000000001.seg       # 数据文件，按首个 msg_id 命名（19 位零填充）
    ├── 000000000000000001.idx       # 该段的索引：id→offset
    └── 000000000000500001.seg       # 达到 64MB 后滚动
```

- 文件名前缀 = 该段**第一条消息的 msg_id**。文件名排序 == msg_id 排序，
  定位时只需文件名比较即可二分，不用读内容。
- 段大小上限 `segment_bytes`（默认 64 MiB），超出滚动新段。

## 2. 记录格式（seg 内）

```
 偏移  长度  字段
 0     2     magic  "CR"
 2     1     version = 1
 3     1     type    1=MSG
 4     4     body_len
 8     4     crc32    覆盖 [2,8)（version/type/body_len）+ [12, 12+body_len)（body）
 12    N     body     TLV 编码
```

> crc 字段本身不参与校验（否则无法自洽）。实现上是两次链式 `crc32()`：
> 先算 6 字节头，再把 body 续算上去。

`body` 的 TLV 字段沿用协议 tag（`MSG_ID/FROM_USER/TS_MS/TEXT/MSG_KIND`），
这样 `cht-dump` 可以直接复用协议解码器，不需要第二套序列化。

**校验策略**：读取时校验 magic + crc32，任一失败视为该记录及之后全部损坏。

## 3. 索引格式（idx 内）

定长 16 字节，升序：

```
msg_id u64 | offset u64
```

- 追加写，与 seg 同生命周期。
- 查询某 id：对该段 idx 做 `pread` 二分 —— 定位到下界后 `pread` seg 取记录。
- 索引可重建（`chatd --repair`）：扫 seg 顺序生成 idx。所以 idx 丢失不是灾难。

## 4. 房间元数据 room.meta

TLV 文本/二进制混合，写入用 **临时文件 + fsync + rename** 保证原子：

```
version u8 = 1
room            str
last_msg_id     u64
msg_count       u64
segment_bytes   u32
segments        array { first_id u64, last_id u64, bytes u64, path str }
```

启动时若 `room.meta` 缺失（首次创建或损坏），通过扫描目录重新生成。

## 5. 写入路径（append + group commit）

```cpp
append(room, from, ts, text):
  lock(room.mu)
  msg_id = last_msg_id + 1
  buf = 编码记录
  pwrite_all(seg_fd, buf, seg_size)         // 顺序追加
  pwrite_all(idx_fd, id+offset, 16)
  seg_size += buf.size(); msg_count++
  last_msg_id = msg_id
  // 同步策略
  if (sync_mode == ALWAYS)  fdatasync(seg_fd)
  else                      pending++; 交给 flush 线程按 2ms 或 1000 条触发
  unlock
  if (sync_mode == ALWAYS) return msg_id   // 已落盘
  else 等待本批次 fsync 完成 (condvar)     // group commit：一批共享一次 fsync
```

- 默认 `sync_mode = BATCH`（2ms 刷盘 + 组提交）。ACK 一定在 fsync 之后发出，
  满足"ACK 即持久"（N7）。
- `sync_mode = NEVER` 只用于压测对比，不能用于生产。
- 写入用 `pwrite`（带显式 offset）而不是 `write`，避免共享文件偏移的隐式状态，
  也让"恢复后截断"逻辑可控。

## 6. 读取路径

```
read_before(room, before_id, limit):
  段 = 二分(segments, before_id)             // 内存数组，O(log S)
  在段内 idx 二分找到 <= before_id-1 的最后一条
  从该记录**反向**逐条 pread 读取，直到 limit 条或段首
  若不足，退到上一段继续
  返回按 id 升序的 vector<Message>
```

- 反向读用 `pread` 每次一条记录头 12 字节取 `body_len`，再读 body。为减少 syscall，
  可一次读 64KB 窗口向后解析（M4 优化项，先做简单版）。

## 7. 崩溃恢复

启动时对每个房间：

1. 读 `room.meta`；失败则全量扫描重建。
2. 对最后一个段：从文件末尾向前扫描（按 8KB 窗口）找最后一个 `magic+crc` 通过的记录，
   `ftruncate` 掉其后的垃圾字节。
3. 校验该段 idx 的行数是否与 seg 记录数一致；不一致则重建该段 idx。
4. 更新 `last_msg_id` 并原子写回 `room.meta`。

只处理尾部损坏：中间损坏意味着硬件故障，此时停止加载该房间并记 `STORAGE_ERROR`，
不静默丢数据（宁可报错，也不做"精确性"的妥协）。

## 8. 容量与性能估算

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| 单条约 100B 文本 | 记录 12 + TLV 约 130B | ≈ 142B |
| 1000 万条 | 142B × 1e7 | ≈ 1.4 GB 数据 + 160 MB 索引 |
| 索引内存 | 不常驻，按需 pread | 常驻 < 16 MB（仅段表） |
| 写入吞吐 | 顺序写 + 批量 fsync | SSD 上 5–20 万条/秒 |
| 随机定位 | 1 次段二分 + 1 次 idx 二分 + 1 次 pread | 亚毫秒 |

## 9. 已知取舍与后续优化

1. 当前 idx 每 16B 一条，1000 万条占 160MB 磁盘；M5 可选"每 64 条索引一次"的稀疏索引
   + 段内扫描，把索引压到 1/64。
2. 未实现段合并/归档删除；M6 可选 `--retain-days`。
3. 单房间写串行（一把 mutex），极端情况热点房间受限；M6 可选分片（按 id 取模分多个 log）。
4. 不使用 mmap：mmap 在大文件随机读上更快，但崩溃时的脏页回收语义更复杂，先保证正确性。
