### 关键决策（与初版设计的偏差）

| 项 | 原设计 | 实际 | 原因 |
| --- | --- | --- | --- |
| epoll 触发模式 | ET（边缘触发） | **LT（水平触发）** | ET 要求必须读到 EAGAIN 且写事件管理更易错；聊天场景连接数在千级，LT 的开销可忽略。已同步修改 01 文档。 |
| 账号存储 | `meta.db` TLV 二进制 | **文本行 `id\tname\tsalt\tdigest`** | 便于人工排查与 `cht-dump` 之外的审计；体积可忽略（账号数少）。 |
| ACK 时序 | 同步 fsync 后返回 | **group commit + 异步回调** | 同步 fsync 每条约 1 ms，吞吐上限 1000/s。改为存储线程批量 fsync，完成后回投 io 线程发 ACK，语义仍是"ACK 即落盘"。 |
| `MSG_SEND_ACK.seq` | 回填请求 seq | **固定 0，用 client_msg_id 匹配** | ACK 由存储线程异步产生，无法保证在同一调用栈回填。协议文档已更新。 |
| 房间 `room.meta` | TLV | **文本 key-value + 段表** | 同上，可读性优先；关键路径不依赖它（崩溃后靠扫描重建）。 |

### 遇到的问题与修复

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | `RoomStore::append` 段满时死锁 | `return append(m)` 重入同一 `std::mutex` | 滚动后原地写入，不递归 |
| 2 | `read_before(0, N)` 返回空 | 找段循环用 `last_id+1 >= UINT64_MAX` 永假 | `before_id==0` 时直接从最后一段倒序读 |
| 3 | e2e 报 "login required"，反复重连 | **`register_user()` 只登记映射，忘了置 `s.authenticated = true`**，后续 JOIN 全被鉴权拦掉 | 在 `register_user` 里置位；客户端收到 `unauthenticated` 时自动重发 LOGIN |
| 4 | 客户端收到消息却卡死不退出 | stdin 是**阻塞**模式，`read` 循环卡在等更多输入，期间 socket 事件得不到处理 | stdin 统一设 `O_NONBLOCK`，用 `EAGAIN` 区分"暂无数据"，`read==0` 才是 EOF |
| 5 | 管道 EOF（`--plain` 脚本模式）不退出 | 管道写端关闭时 `poll` 的 `revents` 只有 `POLLHUP`，没有 `POLLIN`，检查被漏掉 | 事件检查改为 `POLLIN|POLLHUP|POLLERR` |
| 6 | **SIGTERM 直接杀进程，优雅退出完全不生效**（meta 不落盘、无关闭日志） | `log_init` 在 `main` 里创建了日志线程，**信号屏蔽发生在 `Server::start()`，晚于该线程创建**；线程继承未屏蔽的掩码，SIGTERM 落到日志线程上走默认动作 | 在 `main()` 最开头（任何线程创建前）`pthread_sigmask` |
| 7 | `kill -9` 后重启，`room.meta` 仍是崩溃前的滞后值 | 恢复扫描只修正了内存里的 `last_msg_id_`，没回写 meta；且房间懒加载，重启后没人 join 就不会扫描 | `open()` 结束前回写 meta；`StorageManager` 启动时扫描 `rooms/` 目录记录已知房间（`/rooms` 不再只显示已打开的房间） |
| 8 | 压测挂死（`msgs_acked` 永远达不到目标） | 服务端每连接限流 20 帧/秒，被限流的请求只回 `ERROR`，压测工具不处理 → 窗口里的条目永远等不到 ACK | 限流改为可配置 `--rate-limit N`（0 = 关闭，压测用）；`cht-load` 处理 `ERROR` 帧并从窗口移除，另加 120 s 防挂死超时 |
| 9 | `utf8::prev_boundary` / 编辑器中文移动断言失败 | **测试期望值写错**（把字节偏移当字符序号），实现是对的 | 修正测试并注明字节布局 |
| 10 | 段文件尾部损坏后索引错位 | 索引未随截断同步 | `scan_one_locked` 校验 `idx_size == records*16`，不符即重建 |
| 11 | e2e 第二次运行时"通过"了但用的是旧进程 | `pkill` 没执行，端口被上次残留的 chatd 占用，新实例 bind 失败，脚本仍连到旧实例 | 脚本启动前 `pkill -f "chatd --port PORT"`；检测到子进程提前退出立即失败 |
| 12 | PowerShell 下 `bash -lc "…| head"` 报错 | PowerShell 自己解析管道 | 构建/测试逻辑全部收进 `scripts/*.sh`，Windows 侧只调用脚本 |
| 13 | **界面"不刷新"**：新消息不显示、回车后输入行不清空、`/help` 无输出 | ① 屏幕行缓存 `cache_` **只在窗口宽度变化时重建**，新消息永远进不了缓存（状态栏 `msgs` 计数在涨，消息区不动）；② `Renderer::draw` 用 `out.size() > 32` 丢弃"只有光标移动"的小更新，但 `prev_` 已经更新 → 屏幕与内部状态永久不一致，该行之后再也不重绘 | 加 `cache_dirty_` 标志，消息/宽度变化都重建缓存；`draw` 无条件输出；`submit()` 后强制重绘；状态栏每秒刷新一次让时钟走字 |
| 14 | 断线后 `!` 标记的失败消息在重连后消失，Ctrl-R 提示 "no failed message" | `join_ack` 无条件 `msgs_.clear()`，重连时的 join 把本地未确认/失败消息一起清掉了 | 同房间重连且本地有待确认消息时改为**合并**（`merge_older`）而不是清空 |

| 崩溃一致性 | 1000 条 ACK 后 `kill -9`，重启 1000 条一条不少，CRC 全通过，meta 自动修复 |
| ASan/UBSan | 31 个用例在 `-fsanitize=address,undefined` 下全过，无报告 |
| 压测（窗口 4） | QPS **41237**，p50 **1 ms** / p99 **3 ms** |
| 压测（窗口 64） | QPS **72398 – 111888**，p50 3–5 ms / p99 11–17 ms |
| 20 万条 | QPS 110619，p50 4 ms / p99 12 ms，3 段 / 22 MB |
| 1000 万条（直压存储） | **236495 条/秒**，1.03 GB / 14 段，重启恢复 **134 ms** |
| 随机读 10 万次（每次 50 条） | p50 **65 µs** / p99 **226 µs** |
| 浸泡 60 s | 发送 380 万条（951 轮建连），RSS 5.8 → 6.1 MB，0 错误 |
| Ctrl-R 重发 | SIGSTOP 冻结服务端 → 发消息显示 `…` → kill -9 后变 `!` → 重启自动重连（本地失败消息保留）→ Ctrl-R → 落盘 1 条，无重复 |
| 磁盘保护 | `--max-room-mb 1` 灌 2.4 MB：写入 10591 条（≈1 MB），9409 条被拒并记日志，已有数据不受影响 |

**延迟归因**：完全符合 Little's Law（L = λW）。窗口 4 → 在途 32 条 → W ≈ 0.8 ms；
窗口 64 → 在途 512 条 → W ≈ 4.7 ms。p50 由**客户端窗口**决定，服务端单条处理在微秒级。

### 性能优化记录（M5，按收益排序）

| 优化 | 做法 | 效果 |
| --- | --- | --- |
| **批量 flush**（最大收益） | 广播只入队，本轮 epoll 处理完统一写；`writev` 一次合并最多 64 段 | QPS 4017 → 111888，p99 171 ms → 11 ms |
| 共享帧 | 广播帧 `shared_ptr<const string>`，8 个会话共享同一份 | 省掉 8 次整帧拷贝 |
| 单发零分配 | `OutChunk` 用 `own` 承载移动进来的 string，不再 `make_shared` | 去掉每条消息一次堆分配 |
| ~~append 移出 io 线程~~ | 曾把 pwrite 搬到工作线程 | **负优化，已回退**：p50 4→9 ms，QPS 5065→3327 |

> 关键教训：这次的瓶颈不在磁盘 IO（`pwrite` 到 page cache 是微秒级），而在
> 「每条消息逐个会话写 socket」造成的 syscall 放大。先测再优化，否则容易优化错地方。

## 2026-10-30 追加：P2P 模式（阶段 1）

### 需求确认

| 问题 | 用户选择 |
| --- | --- |
| 场景 | 局域网零配置优先，跨网也要能连 |
| 信令 | **必须全自动**（输入用户名就连，不粘贴地址） |
| 公网机器 | 有 VPS，可做信令 + 中继 |
| 消息历史 | 各自存本地 |

由此确定架构：**VPS 上跑 chatsig 做地址交换，客户端尽力直连**。全自动只能靠信令实现——
这是 NAT 的物理限制，不是实现取舍。

### 已完成（阶段 1 + 阶段 4）

1. **协议扩展**（`CHTP` 保持兼容）：8 个信令消息类型（`PEER_REGISTER/LOOKUP/INCOMING/OFFLINE/RELAY_*`）
   + 7 个 tag（`LAN_IP/TCP_PORT/CANDIDATES/PEER_NAME/PUBLIC_IP/PUBLIC_PORT/CAND_KIND`）。
2. **`chatsig`**（约 550 行）：复用 `IoLoop`/`Session`/`Auth`，实现登录、端点注册、
   候选地址查询（lan + public 两条）、`peer_incoming` 推送、离线清理。
3. **`chatt --p2p`**（约 800 行）：同时监听与发起、多对端会话、信令自动重连、
   本地 `RoomStore` 存储（`data/peers/<对端>/`）、专用于 P2P 的终端 UI。
4. 文档 `docs/11-P2P架构.md`（含后续阶段与安全风险）。
5. **中继兜底（阶段 4）**：`RELAY_OPEN/RELAY_ACK/RELAY_DATA`。直连全失败后自动申请，
   双方配对后由 chatsig 原样转发内层帧（不解包）。覆盖双方都在 NAT 后的场景。

### 实测

| 项 | 结果 |
| --- | --- |
| 信令联调（`sig_test.py`） | 注册返回 public_ip/port、查询返回 2 个候选（lan + public）、被叫收到 `peer_incoming`、离线/未知用户返回空候选 —— 全过 |
| P2P 直连（`p2p_test.py`） | alice `/chat bob` → 查信令 → **直连 lan 候选成功** → 双向消息 → 双方各自本地落 2 条记录（`cht-dump` 核对一致） |
| P2P 中继（`p2p_test.py relay`） | 跳过直连申请中继 → 对方自动接受 → 配对成功 → 消息经 chatsig 转发 → 双方本地同样各落 2 条，与直连模式结果一致 |

### 关键设计取舍

| 决策 | 理由 |
| --- | --- |
| 先 TCP 直连，UDP 打洞放到阶段 3 | UDP 需要在自研可靠层上验证，没有 TCP 基线就分不清"打洞失败"和"可靠层 bug" |
| 候选地址 lan 优先 | 同网段直连最快最稳，且完全不过公网 |
| P2P 连接不做登录，靠 `HELLO` 里的用户名标识 | 点对点没有账号中心；**这是已知安全弱点**，阶段 5 用公钥指纹补 |
| 每对端一个 `RoomStore` | 复用成熟的分段日志与崩溃恢复，零新代码 |

### 已知限制

- **跨网可以连上了，但走中继时流量过 VPS**（带宽/延迟成本）。阶段 3 的 UDP 打洞是可选优化。
- 同时只支持**一条中继会话**（跟 A 中继时不能再跟 B 中继）；直连会话可以多条。
- 无法防冒名（任何人可连你的端口并声称是某个用户名），阶段 5 用公钥指纹补。
- 单用户多设备：后注册覆盖先注册。
- 对方离线时不排队消息（本地仍记录你发出的内容）。

### 未做（明确不做，防止范围蔓延）

- 端到端加密（阶段 5 已完成，见下一节）、文件传输、多机集群、图形界面。

## 2026-10-30 追加：阶段 5 端到端加密

### 阶段目标

媒体通道（直连或中继）上的聊天内容端到端加密，并且能发现"冒名顶替"（公钥指纹变了）。

### 已完成

1. **密码学原语全部手写**（`src/common/crypto.{h,cpp}`，约 600 行，不引入 OpenSSL/libsodium）：
   X25519（RFC 7748）、ChaCha20-Poly1305（RFC 8439）、HKDF-SHA256（RFC 5869）、
   SHA-256 指纹。正确性由 4 组官方向量 + 边界用例锁定。
2. **会话密钥派生** `derive_session_keys`：静态 X25519 + 双方一次性随机数 → HKDF 出 64 字节，
   按公钥字节序划分方向（发起方/被叫方、直连/中继都不需要额外协商）。
   *（同日晚些时候升级为四重 DH，见下一节；这里的"随机数"已被"临时公钥"取代。）*
3. **协议**：新消息 `CRYPTO_KEX(0x0080)`，新 tag `KEX_PUB/KEX_NONCE/CIPHER/NONCE`。
4. **客户端**：`data/identity.key` 长期身份密钥（首次启动生成）、
   `HELLO` 之后立即双向握手、`MSG_SEND` 只走密文、接收侧拒绝明文/重放/篡改，
   TOFU 指纹库 `data/known_peers.txt`，`/fingerprint`、`/trust <name>`，状态栏 `e2e:*`。
5. **文档**：`11-P2P架构.md` 新增 §5.6（握手与密文格式）、降级表、阶段表状态；
   本地存储树补 `identity.key`/`known_peers.txt`。

### 关键决策（取舍）

| 决策 | 理由 |
| --- | --- |
| 方向由**公钥字节序**决定，而不是"谁是发起方" | 中继模式下双方都主动申请，没有天然的发起方；字节序是双方都能独立算出的 |
| 握手随机数参与 salt | 每次连接密钥都不同，天然避免 (key, nonce) 重用；等价于给静态密钥加了每会话隔离 |
| nonce 用**计数器**而不是随机数 | 计数器保证唯一性且省一次随机数系统调用；重放检查顺带就有了（序号必须严格递增） |
| 只加密 `text`，`ts_ms` 保持明文 | 加密时间戳会让历史/排序/调试变复杂。**明确承认**：时间与消息长度是可见元数据 |
| 握手没完成时**拒绝发送**，并把内容退回输入行 | "静默失败"比"明文降级"危险得多；用户能立刻看到没发出去 |
| TOFU 而不是"首次弹窗确认" | 终端界面里弹窗成本高；首次记录 + 变更告警 + `/trust` 覆盖，与 SSH 的取舍一致 |

### 遇到的问题与修复（这一轮全是"自研密码学"踩的坑）

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | X25519 两个 RFC 7748 向量全错（公钥、共享密钥、DH 密钥都错） | `fe_sub` 借位修复**符号写反**：回绕等于加了 2^256 ≡ 38，要的是 `f-g`，应该**减** 38 却加了 38，每次减法偏 76 | 借位后减 38；同时补 `fe_weak_reduce` 维持"fe 恒 < 2^255"的不变量 |
| 2 | `fe_tobytes` 输出可能 ≥ p | 只清第 255 位不做规范约简，值落在 [p, 2^255) 时会输出错误编码（概率 19/2^255，靠向量测不出来） | 常量时间条件减 p |
| 3 | Poly1305 tag 全错（密文却是对的） | ① AEAD 的 `pad16` 是**零补齐**，误用了原始 Poly1305 的"末尾补 0x01"；② 还额外喂了一个全零块 | 末块补零后整块带 2^128 位；删除多余块 |
| 4 | tag 仍错，且第 1–3 个字整体偏移 | 末段 `(h1>>6) \| (h2<<20)` 没先 `& 0xffffffff` 就加 pad，`h1<<26` 的高位被当成进位 | 每个 32 位字先截断再加 pad（donna 的写法） |
| 5 | 握手永远停在 `e2e:handshake`，对端收不到公钥 | `kex_send` 用 `peer_send` 入队后没 `flush`，直连路径要等到下一次发送才刷出 | 发送后 flush（中继路径 `peer_send` 内部已 flush） |

定位方法：先用 Python 大整数**逐行复刻**域运算与 Poly1305，把"算法错"和"实现错"分开；
再用独立整数版 Poly1305 与 RFC 向量对齐，锁定偏差发生在最后序列化而不是块运算。
**教训：自己实现的密码学，必须有一个独立实现来对照，否则"两边一起错"是查不出来的。**

## 2026-10-30 追加：前向保密（阶段 5 收尾）

### 阶段目标

上一节的会话密钥是**静态-静态 DH**：谁事后拿到身份私钥，就能解开当时录下来的全部流量。
目标是"临时私钥用完即弃，事后只有身份私钥也解不开历史连接"。

### 改动

1. `derive_session_keys` 改为**四重 DH**（`crypto.h`/`crypto.cpp`）：
   `DH(id,id) ‖ DH(eph_小,id_大) ‖ DH(id_小,eph_大) ‖ DH(eph,eph)` → HKDF(info=`chatt-p2p/v2`)。
   四段各管身份绑定 / 临时挂身份 / 前向保密，缺一段都算不出来。
2. 协议：握手帧的第二个字段从"一次性随机数"换成"一次性**公钥**"
   （`KEX_NONCE` → `KEX_EPH`），随机数的职责由临时密钥本身承担，少一个字段少一份出错空间。
3. 客户端：每个连接 `x25519_generate()` 一把临时密钥，派生成功后立刻 `memset` 私钥。
4. 独立实现（`scripts/e2e_sec_test.py`）同步改成四重 DH，继续做互操作对照。

### 遇到的问题与修复

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 单测里 A 的 `recv` ≠ B 的 `send`（`send` 方向却对得上） | 四段 DH 用"我的临时×对方身份"和"我的身份×对方临时"按本地视角串接，**两端顺序相反**；而 `DH(eph_a,id_b)` 与 `DH(id_a,eph_b)` 是两个不同的值 | 串接顺序改成按**身份公钥字节序**规范，两端算出同一串（这一处错误是单测先发现、再用独立 Python 实现复核的） |

### 实测

| 项 | 结果 |
| --- | --- |
| 单测 | 42 个用例全过，0 编译警告；`session_keys_agree` 增加"同输入可复现""换临时密钥即换密钥""临时公钥低阶点拒绝" |
| 互操作（`e2e_sec_test.py`） | 纯 Python 独立实现的四重 DH 与 C++ 完全一致（双向解密成功），重放/篡改/明文拒绝全部仍然成立 |
| P2P（`p2p_test.py` 直连 + 中继） | 消息互通、指纹互验一致 |
| ASan/UBSan | 全过，无报告 |

### 说明（FS 的边界，别夸大）

- 这是**连接级**前向保密：临时私钥销毁后，历史连接不可再解；但一条连接内部的消息共用会话密钥。
- 主动中间人在握手时替换公钥仍然可行——**靠指纹比对发现**，这一点没有变化
  （要根治需要签名 + 证书固定，属于后续）。
- 临时私钥只在内存里，进程崩溃即可，没有落盘。
